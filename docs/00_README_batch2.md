# Артефакты: N1/N2 fix + roadmap-шаги по ускорению

## Порядок прогона

1. **`01_n1_n2_fix.diff`** — применить первым. Без этого `02` не запустится
   (все конструкции `KernelConfig(use_centering=True)` в тестовых файлах
   упадут на `NotImplementedError`).

2. **`02_test_regressions_bundle.py`** — `pytest 02_test_regressions_bundle.py -v`.
   Чисто CPU, TPU не нужен. Закрывает:
   - guard по `group` (формула вместо `_MAX_VALIDATED_GROUP=16`),
   - регрессию P0.1/P0.2 (wy_eps/clip plumbing) + N5 (`extreme_large_kb`),
   - регрессию P0.3 (centering gate) + N3 (`DEFAULT_CONFIG` дефолт).
   Требует, чтобы `_max_validated_group` уже была добавлена в
   `gdn2_fwd_batched.py` (формула из прошлого ответа — включена сюда как
   часть теста, но саму функцию в модуль нужно вставить отдельно).

3. **Baseline** — прогнать `full_fwd_bwd_efficiency.py` БЕЗ ПРАВОК на
   реальном TPU, сохранить вывод. Это единственная точка "до" для всех
   девяти кернелов сразу — без неё пункты 4-7 ниже оптимизируют вслепую.

4. **Выбор стратегии `b_batch_group`** — выбрать ОДИН из двух вариантов
   по результатам (3):
   - **`03a_variant_fixed_group.diff`** — если shape'ы стабильны
     (train_shape не меняется от сессии к сессии). Дёшево, ноль рантайм-
     оверхеда, но требует ручного обновления при смене `bt/bc/dtype`.
   - **`03b_variant_autosearch_group.py`** — если ожидаете дрейф
     shape'ов/железа между Kaggle-сессиями. Платите один пробный прогон
     на новую комбинацию `(bt,bc,dtype,n_chunks,vmem_limit_bytes)`,
     дальше кэш.
   Не применять оба одновременно — они конфликтуют по тому, кто
   выставляет `b_batch_group`.

5. **`04_use_fused_ab_patch.diff`** + **`05_test_use_fused_ab.py`** —
   подключение fused A+B к inference-only `gdn2_pallas_forward` за флагом.
   Тест — CPU/interpret=True smoke test. Перед включением где-либо
   пользовательском — обязателен прогон `gate1_wy_solve_batched.py`
   секции (A2) с `interpret=False` на вашем train_shape (не на игрушечном
   CPU-шейпе, который там сейчас захардкожен).

6. **`06_gdn2_bwd_batched_b2.py`** + **`07_test_b2_batched_vs_nonbatched.py`**
   — Hypothesis G (MB8), первый и самый дешёвый шаг Фазы 3 backward-
   батчинга. B2 выбран первым намеренно: два прямых матмула, без цикла,
   без scatter — не тот класс риска, что уже один раз ломал Kernel B
   (`.at[].set()`) и потенциально ждёт в B3/B4.
   `07` использует реальные residuals из forward (через
   `_build_real_residuals`), а не игрушечные тензоры — тот же принцип
   honest-benchmarking, что в `full_fwd_bwd_efficiency.py`.
   **Прогнать на CPU (`interpret=True`, уже стоит по умолчанию), затем
   ОБЯЗАТЕЛЬНО повторить с `interpret=False` на TPU** — CPU-прохождение
   доказывает только "математика не изменилась", не "лоуерится на Mosaic"
   (тот же caveat, что для fused A+B в gate1-файле).

## Что не входит в этот набор (осознанно)

- **B3/B4 батчинг (Фаза 3, оставшаяся часть)** — сознательно не даю
  прототип. По вашей же оценке риска это самый опасный код (уже один раз
  ловил double-damping bug, плюс scatter-паттерн `dgc_ref[...,i0:i1] = ...`
  внутри цикла — тот же класс, что ломал Kernel B). Делать после того,
  как B2 (и логически следующий за ним B5) пройдут Gate 1/2 на TPU, с
  уже наработанным на них паттерном "list-of-blocks + concatenate вместо
  .at[].set()", а не по аналогии.
- **H2 (n_micro-батчинг внутри Kernel B)** и **H4 (bsz/H как ось)** —
  не даю прототип: оба требуют отдельного дизайн-решения о том, как это
  сочетается с уже существующим batch-по-n_chunks (VMEM-бюджет общий,
  наивное умножение осей может OOM'ить непредсказуемо — то, о чём
  предупреждает сам `Fwdbwd_14ms_roadmap.md`, §7). Стоит начинать после
  того, как понятны реальные числа из baseline (шаг 3).
- **H7/H8 (precision, bf16 storage)** — намеренно не сейчас, по вашей же
  floor-модели grid-dispatch overhead доминирует на 1-2 порядка над
  compute/memory; оптимизировать precision раньше значит чинить не то
  узкое место.
